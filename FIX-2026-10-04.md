# Forge Console — Fix Brief (2026-10-04)

User feedback on the live console at :8903. Six items: five design/bug fixes on the Flow
tab + one data bug on the Insights tab. All in `web/app.js` (+ tiny HTML tweak for legend)
and `collector.py` (item 4). Keep the vanilla-JS stdlib-only architecture — no frameworks,
no build step, no new dependencies.

## Design constraints (user-approved)
- The Insights and Ideas pages keep their current background (cubes motif etc.) UNTOUCHED.
- "Dark background with a grid" refers to the FLOW CANVAS ONLY: the flow tab gets a dark
  background with a subtle grid (graph-paper / node-editor look). Do NOT add a grid to the
  other tabs.
- Nodes are SQUARES (Blender / Nuke / Unreal node style), not circles. Text goes ON the
  node face (title inside, sub-label below or inside), like compositing software nodes.
- Particles (travelling dots) only on edges with REAL activity. No idle-edge dots.

## Item 1 — Grid background on the Flow canvas
Add a grid to the flow canvas render (dark bg already there; the grid should pan/zoom with
the world so it feels like a node editor surface). Faint lines, e.g. major/minor grid with
colors like rgba(255,255,255,0.04) minor / 0.07 major, spacing ~40px world units. Keep it
subtle. It must account for pan/zoom (draw in world space inside the existing translate).

## Item 2 — No dots when nothing is flowing
Currently `updateFlowParticles` spawns on any edge where `edge.density !== 0`, and edges
carry `density: 1` even for inactive (idle) edges (see `buildFlowGraph`: harness idle edges
density 1, service→db edges density 1, project inactive edges density 0). Idle edges must
NOT spawn particles at all. Simplest correct rule: only spawn when `edge.active` is true
AND `edge.density > 0`. Also make `buildFlowGraph` set `density: 0` on idle edges (harness
idle: density 0; the always-on `service→db` reader edges: those represent the reader
relationship — give them density 0 too unless the service is green/active AND its db was
written recently; simplest: density 1 only when `edge.active`). Verify: with all harnesses
idle and no recent fs writes, the canvas shows zero moving dots.

## Item 3 — Square nodes with text inside
Replace the circle rendering for all nodes (harness, filesystem, project, service,
database) with rounded rectangles (Nube/Unreal style). Requirements:
- Node size derived from content: width ~ max(110, text width + padding), height ~46-56.
  Give each node type a sensible width; harness/service nodes can be wider (~150).
- Title text INSIDE the box (top area, semibold 11-12px), sub-label (status/size) inside
  below it or just under the box (10px mono, muted). Active nodes: accent-colored border
  + subtle accent glow (shadowBlur) + a small accent "power" dot or left-edge stripe;
  inactive: dim border (rgba(255,255,255,0.18)), dark fill (#141416-ish), no glow.
- Selected node: white border; hovered: brighter accent border.
- `hub-forge` can stay special (hex or a larger accent square with the glyph) but must be
  consistent with the square language.
- `hitTestFlowNode` currently uses `n.radius` circles — update to rectangle bounds (use
  `n.w`/`n.h` half-extents stored on the node). Tooltip/click must still work.
- Keep `state.flow.hoveredNode`/`selectedNode` logic working.

## Item 4 — One "insights node" (data stores) instead of 5 DB nodes
Instead of 5 separate database nodes (hermes state.db, opencode.db, scheme board.db,
hermes cron, hermes logs), render ONE wider square node — conceptually the "insights /
data stores" node — with MULTIPLE labeled ports (Nube-style) on its top edge, one port
per store: hermes state, opencode db, scheme board db, hermes cron, hermes logs. Each
port shows its name; ports whose store was written recently (last_write_age_s < ~300)
get an accent highlight/pulse so you can see which store is receiving writes.
- Data: `collector.py get_databases()` already returns per-store `last_write_age_s`,
  `size_str`, `reader` — reuse it as-is (no collector change strictly required; you may
  add an `is_hot` bool but the JS can compute it).
- Edges: replace the 5 db→hub edges with a single node→hub edge (active if any store is
  hot). Keep the service→specific-db edges but route them to the correct PORT on the
  insights node (insights-board / hermes gateway → "hermes state" port; scheme-board →
  "scheme board db" port). Ports: hermes state (insights board + gateway read), opencode
  db (insights board reads), scheme board db (scheme board reads), hermes cron, hermes
  logs (gateway). The port layout should visually group by reader so the connections make
  sense.
- Tooltip + click drawer for this node: show the 5 stores with size + last-write age
  (data is in `doc.databases` — attach as `node.stores = doc.databases`).
- Update the HUD legend text ("Data DB" → "Data Stores") if needed.

## Item 5 — Flow page blank after leaving and coming back
ROOT CAUSE (diagnosed): the render loop self-terminates when `state.activeTab !== "flow"`
(`renderFlowLoop` early-returns WITHOUT scheduling the next RAF), and `switchTab`→
`resizeFlowCanvas` sets the canvas to hidden/zero size then clears it; when the user
returns, `switchTab` only calls `resizeFlowCanvas()` again — nothing ever restarts the
RAF loop, so the canvas stays blank until a full page reload.
FIX: make the RAF loop persistent: `renderFlowLoop` must ALWAYS reschedule itself (even
when the tab is hidden — skip the expensive draw while hidden, but keep the chain alive).
In `switchTab`, when returning to flow: `resizeFlowCanvas()` + force an immediate
`drawFlowScene()` so the first frame appears instantly. Alternative acceptable fix:
guard `initFlowTab` to start the loop exactly once (it's already called once since flow
is the active pane at load — but `handleHashRoute` can start on another tab) and in
`switchTab`'s flow branch ensure the loop is running. Either way verify: flow → insights
→ flow shows a rendered canvas immediately, no reload needed. Also verify the 5s
`fetchFlowData` interval keeps updating while away (it already does).

## Item 6 — Insights "ALL" source shows the C6 number (1.4M) instead of the sum
ROOT CAUSE (diagnosed): `getActiveSourceData()` returns `data.summary` for BOTH the `c6`
source and the `all` source (line ~467 in web/app.js: `return data.summary; // 'c6' or
'all'`). So the KPI block, flow chart, and cost section for "ALL" are just the C6/
hermes summary again — which is exactly why the total shows 1.4M when c6 alone is 1.4M.
The source-picker bar is fine because `updateSourcePickCounts` computes the true total
(`c6 + opencode + claudecode + antigravity` billed).
FIX — build a proper merged "all" view for `src === "all"`:
- KPIs: sessions = summary.sessions + opencode.sessions + claudecode.sessions +
  antigravity.sessions; messages/tools/api_calls fall back to summary (the three
  external sources don't report messages/tools — show summary values or omit);
  billed tokens = sum of the four `billed_tokens` (or `total` dicts — c6 uses
  `summary.billed_tokens`, the others have `total.input_tokens + output_tokens +
  cache_write_tokens` == billed; the per-model `billed_tokens` sums already match what
  the pick bar shows, so use the same numbers as `updateSourcePickCounts`);
  cost = summary.estimated_cost_usd + opencode.total.reported_cost_usd +
  claudecode.total.reported_cost_usd + antigravity.total.reported_cost_usd.
- Flow chart for "all": merge the four daily series by date (sum input/output/
  cache_read per date; summary's daily comes from `data.activity.daily` — verify its
  date keys line up; c6 daily is the hermes sessions' daily activity).
- Models table for "all" is already correct (concatenates all four) — leave it.
- The `renderInsightsKPIs` fallback chain (`s.sessions !== undefined ? ...`) currently
  masks the bug because `data.summary` always has those fields; after the fix, make the
  merged object explicit so the fallbacks aren't needed for "all".
Verify after fix (curl the live endpoints, days=7, 2026-10-04):
- c6 billed = 8,179,910 (~8.2M? NO — the KPI "1.4 m" the user saw is TOTAL tokens 1.4M?
  Actually confirm against live data: summary total_tokens=73.3M, billed=8.2M; the pick
  bar showed ~1.4M-ish for c6 depending on the metric/day window — just verify the
